# Great Scale — Levels 6501–6600: receipt-contract conformance

**Status:** source-derived integration finding, documented on the existing PR #89 research branch. This is a design/test note, not a claim that the official suites passed. No code was changed by this note.

## Finding: the canonical receipt and the promotion gate have different schemas

The canonical script `scripts/verify-local.sh` writes `great-scale.verification-receipt/v1` with these fields:

- `schema`, `commit`, `node`, `npm`, `python`
- `javascript_suite`, `python_descent_suite`, `overall`, `created_utc`
- `github_run_id`, `github_run_attempt`, `github_repository`, `github_sha`, `runner_name`

In `promotion_gate.js`, `plainDataRecord` enforces an exact field set for each record. Its expected receipt fields are only:

`schema, commit, overall, javascript_suite, python_descent_suite, github_run_id, github_repository`

Consequently, passing the canonical JSON receipt object directly as `evidence.receipt` to `evaluatePromotionEvidence` is rejected for unexpected fields. The current `test_promotion_gate.js` fixture avoids this integration path by constructing a reduced seven-field receipt inline. This creates a contract mismatch between the producer, test fixture, and consumer.

This conclusion follows from the committed source schemas; the official tests were not run in this session. The issue is not proof that the gate can be bypassed. It is a deterministic interoperability defect that can prevent valid real evidence from being accepted, unless an undocumented adapter projects the receipt first.

## Related binding gap

The canonical receipt includes `github_sha` and `github_run_attempt`, but the gate's receipt schema does not accept or validate those fields. The gate binds `receipt.commit` to the candidate and `receipt.github_run_id` to `run.id`; it does not currently bind the receipt's own `github_sha` or run attempt. The gate's run record also has no `run_attempt` field.

A run ID alone is not a complete execution identity because a workflow run can be retried. Evidence should identify the run attempt and bind it consistently across platform metadata, receipt, job, and artifact.

## Formal contract

Let (P) be the canonical receipt producer, (N) an optional normalization adapter, and (V) the promotion verifier.

[
P(C,R) 	o E_{raw}, qquad V(N(E_{raw}),R) 	o {mathrm{BLOCKED},mathrm{ELIGIBLE}}.
]

For reliable composition, the contract requires either:

1. (V) explicitly accepts and validates the complete versioned receipt schema emitted by (P); or
2. (N) is a documented, tested, loss-aware adapter that validates the full raw schema and produces the verifier's canonical typed input.

Silently discarding binding fields is not acceptable. In either design, require:

[
SHA_{candidate}=SHA_{PR-head}=SHA_{run}=SHA_{receipt.commit}=SHA_{receipt.github\_sha}
]

and:

[
Attempt_{run}=Attempt_{receipt}=Attempt_{artifact}.
]

The exact fields available from the platform must be established by the authenticated collector; they must not be fabricated by a caller.

## Required regression tests

Before promoting the PR, add tests using the actual JSON object generated by `scripts/verify-local.sh`, not only a hand-written reduced fixture:

1. A canonical v1 receipt with all producer fields is accepted after explicit schema validation/normalization.
2. A receipt whose `github_sha` differs from candidate SHA is blocked.
3. A receipt whose run attempt differs from the authenticated run attempt is blocked.
4. A receipt with a missing, malformed, or unknown required field is blocked.
5. A receipt from a different repository, run, or artifact is blocked.
6. A fixture containing unrecognized fields is rejected unless the versioned schema explicitly permits them.
7. A producer-schema change fails a contract test until the verifier or adapter is deliberately updated.
8. A current candidate SHA change after test execution invalidates the prior receipt for promotion.

The acceptance fixture should be created by calling the same receipt-writing logic used by `scripts/verify-local.sh` (or by sharing a schema module), not by duplicating a simplified object in the test.
